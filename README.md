# Karwa Phase 72 / 2.2.3

## جديد Phase 72 — سلة متعددة الأصناف
يمكن للعميل طلب صنف واحد أو عدة أصناف من نفس المطعم أو مزود الخدمة، مع كمية ووحدة مستقلة لكل صنف وإجمالي موحد وتعديل الكميات قبل استلام مندوب التوصيل.

## جديد Phase 71 — تعديل الطلب قبل استلام مندوب التوصيل
- صاحب الطلب فقط يستطيع تعديل طلب المطعم/الخدمة، كما يستطيع تعديل تفاصيل طلب توصيل الأغراض المباشر، حتى مرحلة الاستلام المؤكد (statusIndex 3).
- إذا قبل مندوب التوصيل الطلب أو وصل إلى النشاط، يبقى التعديل متاحًا حتى إدخال رمز الاستلام فعليًا.
- عند الحفظ يعاد حساب subtotal و totalPrice ذريًا، وإذا كان هناك طلب توصيل مرتبط يتم تحديث serviceTotal في نفس Firestore Transaction.
- بعد استلام المندوب يظهر للعميل قفل واضح وتمنع Firestore Rules أي تعديل متأخر حتى لو تم العبث بالواجهة.
- مزود الخدمة يرى عدد مرات تعديل العميل وأحدث كمية/ملاحظات لحظيًا.


أضيف سجل إلغاء موحد: كل إلغاء من عميل أو كابتن أو مزود خدمة أو الإدارة يتطلب سببًا واضحًا، ويحفظ هوية الملغي واسمه وبريده ونوع حسابه ووقت الإلغاء، وتعرضه لوحة الإدارة مباشرة. راجع `README-PHASE70-AR.md`.

أضيف إكمال تلقائي احتياطي لرحلات التكسي عند نسيان رمز الوصول: إذا بقيت الرحلة في مرحلة «وصل الكابتن» ثم أصبح العميل والكابتن معًا قرب الوجهة المطلوبة عبر GPS دقيق، تُغلق الرحلة تلقائيًا بعد تحقق قصير. لا يحدث خصم مزدوج؛ يشترط النظام أن رسوم كروة للطرفين محسوبة أصلًا وفق نظام المحفظة الحالي. راجع `README-PHASE69-AR.md`.

# Karwa Phase 61 — تحقق بلاغات الطريق بدون Cloud Function

- تم نقل تحقق بلاغات الطريق فقط من `verifyRoadReport` إلى Firestore `runTransaction()` مباشرة.
- التنبيه يبقى عند 150 متر، وتظهر نافذة التحقق لمدة 6 ثوانٍ عند الوصول.
- «نعم» يبقي البلاغ ويبدأ جولة تحقق جديدة، و«لا» الأولى تنتظر كابتنًا ثانيًا مختلفًا، و«لا» الثانية تخفي البلاغ من جميع الخرائط (`active=false`).
- كل تصويت يُسجل في `roadReportVerifications` كسجل تدقيق مرتبط بالكابتن وجولة التحقق.
- قواعد Firestore تتحقق من دور الكابتن، حداثة موقعه المسجل، قربه من البلاغ (حوالي 120م)، وتمنع نفس الكابتن من احتساب تصويتين في الجولة نفسها.
- لا تحتاج ميزة تحقق بلاغات الطريق إلى نشر `verifyRoadReport` Cloud Function بعد الآن.
- **مهم:** بقية Cloud Functions الموجودة أصلًا في كروة (مثل بعض عمليات الطلبات والإشعارات الخلفية) لم تُلغَ بهذه المرحلة.
- للنشر: ارفع ملفات Hosting ثم انشر `firestore.rules`.

# Karwa Phase 60 — التحقق الميداني الذكي من بلاغات الطريق

- تنبيه للكابتن عند الاقتراب من بلاغ طريق لمسافة 150 متر مع إشعار الجهاز والصوت/الاهتزاز عند تفعيلها.
- عند الوصول الفعلي إلى موقع البلاغ تظهر نافذة تحقق لمدة 6 ثوانٍ تسأل: هل لا يزال البلاغ موجودًا؟
- إجابة «نعم» تبقي البلاغ وتلغي أي أصوات نفي سابقة.
- إجابة «لا» الأولى لا تحذف البلاغ؛ تسجل انتظار تأكيد كابتن ثانٍ مختلف.
- إجابة «لا» من كابتن ثانٍ مختلف تؤرشف البلاغ ثم تحذفه من الخريطة تلقائيًا.
- ملاحظة تاريخية: في Phase 60 كان التحقق يعتمد على Cloud Function؛ في Phase 61 نُقل هذا التحقق إلى Firestore Transaction + Security Rules.
- يلزم نشر `firestore.rules` ونشر Cloud Functions داخل `backend-notifications` بعد هذا الإصدار.

# Karwa — Phase 60: ربط Phase 58 + تحديث حي + إشعارات Android

- تطبيق Android يستخدم ملفات `karwa0.web.app` أولًا بدون كاش، والنسخة المدمجة Phase 58 كـ Offline fallback.
- عند العودة للتطبيق بعد 25 ثانية أو عند تغيّر `version.json` يتم جلب أحدث ملفات السيرفر تلقائيًا.
- Firebase Hosting مضبوط على `no-cache/no-store` لملفات HTML/JS/CSS/JSON.
- إشعارات Android تظهر في النافذة المنسدلة بقنوات منفصلة للطلبات والمحفظة والنظام، مع صوت النظام واهتزاز.
- رمز FCM يسجل تحت حساب العميل/الكابتن/الخدمات/الإدارة، وإشعار FCM يفتح المسار المرتبط عند الضغط عليه.
- مركز إشعارات الكابتن من Phase 58 محفوظ، وتم ربطه بإشعارات Android الأصلية.
- تم الحفاظ على إصلاح التسجيل من Phase 54 لمنع سباق `onAuthStateChanged` أثناء إنشاء حساب العميل.

## النشر
1. ارفع محتويات حزمة السيرفر المطابقة إلى Firebase Hosting ثم نفذ `firebase deploy --only hosting`.
2. انشر `firestore.rules` عند تغير القواعد.
3. لن تحتاج APK جديدًا لتغييرات HTML/CSS/JS؛ تعديلات Java/Manifest فقط تحتاج بناء Android جديد.
4. لإشعارات الخلفية انشر مجلد `backend-notifications/functions` حسب README الخاص به.

# Karwa0 — Phase 52: رسوم ثابتة، محافظ لجميع الأدوار ورصيد ترحيبي

## التعديلات في هذه النسخة

- لوحة الإدارة تتحكم الآن في **تسعيرة الكيلومتر** لفئات اقتصادي/تكسي/عائلي، وتستمر أجرة الرحلة في مراعاة المسافة ووقت المسار وتقدير الازدحام.
- ألغيت العمولة النسبية واستبدلت بـ **رسوم ثابتة** قابلة للتعديل من الإدارة: رسم نشر النشاط (افتراضي 1,000 د.ع)، رسم العميل لكل طلب (250)، رسم صاحب المطعم/الخدمة عند قبول الطلب (250)، ورسم الكابتن عند قبول الرحلة أو التوصيل (250).
- خصم الرسوم مرتبط بالمحفظة وبنفس عملية إنشاء/قبول الطلب، لذلك لا تُنفذ العملية إذا كان الرصيد المتاح غير كافٍ.
- الشحن متاح للعميل والكابتن ومزود الخدمة. كل طلب شحن يصل إلى الإدارة ومعه **نوع التسجيل**: عميل / كابتن / خدمات أخرى، واعتماد 10,000 د.ع يضيف 10,000 د.ع إلى الرصيد المشحون.
- الحساب الجديد يحصل افتراضيًا على **1,000 د.ع رصيد مجاني لمدة 24 ساعة**. الرصيد المجاني منفصل عن الرصيد المشحون ويُستخدم أولًا، ويمكن للإدارة إيقاف منح الرصيد المجاني للحسابات الجديدة أو تغيير قيمته ومدته.
- مزود الخدمة يدفع رسم النشر عند نشر النشاط لأول مرة بعد اعتماد الإدارة، ثم رسمًا ثابتًا عند قبول كل طلب.
- الكابتن يدفع رسمًا ثابتًا عند قبول طلب الركوب أو التوصيل، والعميل يدفع رسمه عند إنشاء الطلب.
- ما زال الشحن المحلي عبر Mastercard يعتمد على تحويل خارجي + مرجع عملية + موافقة الإدارة، ولا يحفظ التطبيق PIN أو CVV أو كلمات مرور البطاقة.
- عولج في المرحلة السابقة زر الموقع ليجلب GPS وينقل الخريطة مباشرة، مع منع تراكم طلبات المسار والعنوان.

## مهم قبل النشر

1. انشر `firestore.rules` الجديدة **قبل اختبار الرسوم والمحافظ**؛ القواعد الجديدة جزء أساسي من الخصم الذري وحماية الرصيد.
2. من لوحة الإدارة افتح قسم **التسعير والرسوم والشحن** واضبط سعر الكيلومتر، الرسوم الثابتة، إعداد الرصيد المجاني، ومعرف التحويل المحلي.
3. ارفع ملفات الواجهة كاملة؛ تم رفع Service Worker وملفات JavaScript إلى Phase 52 لتقليل بقاء نسخة PWA قديمة.
4. الشحن الحالي **مراجعة محلية بإيصال/مرجع تحويل** وليس خصمًا آليًا من Mastercard. للخصم الآلي يلزم مزود دفع مرخص وبيانات تاجر/API مناسبة.

# Karwa0 — Phase 48: رمز استلام من المطعم/صاحب الخدمة

## الجديد في هذه المرحلة

- طلبات **المطاعم والخدمات** تستخدم الآن رمز تحقق مكوّنًا من 4 أرقام عند نقطة الاستلام.
- يظهر الرمز لصاحب المطعم/مقدم الخدمة داخل بوابته بعد تفعيل طلب التوصيل.
- عند وصول الكابتن إلى المطعم أو النشاط، لا يستطيع الانتقال إلى مرحلة «في الطريق إلى العميل» إلا بعد إدخال الرمز الصحيح الذي يعطيه له صاحب النشاط.
- يبقى رمز العميل النهائي مطلوبًا عند التسليم للعميل كما في المرحلة السابقة.
- **طلبات التكسي لم تتغير**: رمزها الحالي يبقى عند بدء الرحلة.
- قواعد Firestore تتحقق من رمز الاستلام في انتقال حالة الطلب، وليس مجرد إخفاء/إظهار في الواجهة.

> مهم: انشر ملف `firestore.rules` الجديد، ثم ارفع ملفات الواجهة. تم تحديث Service Worker إلى Phase 48 لمنع بقاء نسخة PWA قديمة.

# Karwa0 — Phase 44: فصل طلبات التكسي والتوصيل

## التعديل الجديد
- كابتن التكسي المسجل بخدمة `taxi` يرى ويقبل طلبات الركوب `ride` فقط.
- كابتن التوصيل المسجل بخدمة `delivery` يرى ويقبل طلبات التوصيل فقط: الأغراض `parcel`، الطعام القديم `food`، وتوصيل المطاعم/الخدمات `serviceDelivery`.
- الدراجة مخصصة لخدمة التوصيل ولا يمكن تسجيلها أو اعتمادها كتكسي.
- السيارات يمكنها العمل بالتوصيل فقط عندما يكون الحساب مسجلًا ومعتمدًا بنوع خدمة `delivery`.
- الفصل مطبق في واجهة الكابتن، منطق قبول الطلب، اعتماد الإدارة، وقواعد Firestore؛ لذلك لا يعتمد على إخفاء الواجهة فقط.
- طلبات التوصيل تستخدم رمز العميل عند التسليم النهائي، بينما طلب التكسي يبقى رمز الرحلة عند البدء.

## مهم بعد التحديث
انشر `firestore.rules` الجديدة ثم ارفع ملفات الواجهة. تم رفع أرقام إصدارات الملفات وService Worker إلى Phase 44 لتقليل بقاء نسخة قديمة في ذاكرة PWA.

# Karwa Phase 11 — Spark Edition

هذه النسخة معدلة للعمل في العمليات الأساسية بدون Cloud Functions: إنشاء الرحلة، قبول الكابتن، تحديث مراحل الرحلة وإلغاء الراكب تتم مباشرة عبر Firestore مع Transaction عند القبول.

# Karwa0 — Phase 7: Accounts, Security & Notifications

هذه المرحلة تنقل العمليات الحساسة من المتصفح إلى Backend موثوق باستخدام Firebase Cloud Functions، وتجهز المشروع للمصادقة بالهاتف، Push Notifications، محافظ الكباتن، سجل التدقيق ووثائق التحقق.

## أهم ما تغير
- `functions/index.js`: إنشاء رحلة وتسعيرها على الخادم، قبول الطلب Transaction آمن، انتقال حالات الرحلة، التحقق من OTP على الخادم، إلغاء العميل، تسجيل Push Token، وإنشاء قيود أرباح الكابتن.
- لم يعد OTP الخام محفوظًا داخل مستند `orders`. الطلب يحفظ `tripOtpHash` فقط، والرمز الخام في `orderSecrets` لا يستطيع قراءته إلا صاحب الطلب.
- عند إكمال الرحلة ينشأ قيد في `walletTransactions` بقيمة الرحلة والعمولة وصافي مستحق الكابتن وحالة `pending_settlement`.
- `auditLogs` يسجل إنشاء/قبول/تقدم/إكمال/إلغاء الرحلات من الخادم.
- `firestore.rules` تمنع العميل أو الكابتن من تعديل السعر والعمولة وأرباح الرحلة أو مراحلها مباشرة؛ الرحلات الحساسة تمر عبر Cloud Functions.
- `phone-auth.js`: وحدة جاهزة لـ Firebase Phone Auth + reCAPTCHA لإرسال والتحقق من OTP الحقيقي للهاتف.
- `push-notifications.js` و `firebase-messaging-sw.js`: بنية Web Push وFCM مع حفظ الرموز من خلال Backend.
- `storage.rules`: مساحة آمنة لوثائق الكابتن (صور/PDF حتى 5MB) مع وصول الكابتن نفسه أو الإدارة.
- `firebase.json`: إعداد موحد لنشر Functions + Firestore + Hosting.

## النشر
1. من Firebase Console فعّل Authentication ثم Phone provider، وأضف نطاق الاستضافة إلى Authorized domains.
2. فعّل Cloud Messaging وأنشئ Web Push certificate (VAPID key)، ثم استدعِ `enableKarwaPush()` بالمفتاح العام فقط.
3. ثبّت Firebase CLI وسجّل الدخول ثم داخل مجلد المشروع نفّذ `firebase deploy --only functions,firestore:rules,storage,hosting`.
4. تحتاج Cloud Functions عادةً مشروع Firebase بخطة تسمح بالنشر والفوترة حسب إعدادات Firebase الحالية.

## ملاحظات أمنية
- لا تضع مفاتيح خادم أو Service Account داخل HTML/JavaScript.
- Firebase Web API key الظاهر في الواجهة ليس سرًا بحد ذاته؛ الحماية الفعلية تعتمد على Authentication وSecurity Rules وApp Check وBackend authorization.
- قبل الإنتاج فعّل Firebase App Check، سياسات الاحتفاظ بالسجلات، وراقب تكلفة/حدود OSRM أو استخدم مزود Routing إنتاجي.
- التسوية المالية في هذه المرحلة Ledger داخلي وليست تحويلًا مصرفيًا فعليًا. إضافة بوابة دفع/سحب تتطلب مزود دفع مرخص وتدفقات تحقق خاصة به.

## بنية Phase 7
- `index.html`, `app.js`: تطبيق الراكب.
- `driver.html`, `driver.js`: بوابة الكابتن؛ قبول/تقدم الرحلة عبر Cloud Functions.
- `admin.html`, `admin.js`: لوحة الإدارة الحالية.
- `functions/`: Backend الموثوق.
- `firestore.rules`, `storage.rules`: صلاحيات البيانات والوثائق.
- `phone-auth.js`: مصادقة الهاتف القابلة للدمج في واجهات الدخول.
- `push-notifications.js`, `firebase-messaging-sw.js`: Push Notifications.

- نظام كوبونات server-side يدعم نسبة أو مبلغ ثابت، حدًا أدنى للرحلة، سقف خصم وتاريخ انتهاء.
- رسوم إلغاء بعد قبول الكابتن (حاليًا 1,500 د.ع) مع تعويض يسجل في محفظة الكابتن.
- حفظ baseFare و surgeMultiplier و discountAmount و dispatchCandidateIds داخل الطلب للتدقيق المالي والتشغيلي.

## Phase 10 — Production UX, PWA & Service Areas
- أضيف `manifest.webmanifest` وService Worker لتثبيت كروة كتطبيق PWA على الهاتف، مع App Shell مخزن محليًا وتجربة أفضل عند ضعف الشبكة.

### إعداد مناطق الخدمة
أنشئ مستندًا في `serviceAreas` مثل `mosul-center` بالقيم: `active: true`, `name: "مركز المدينة"`, و`polygon` كمصفوفة نقاط `{latitude, longitude}` مرتبة حول حدود المنطقة (3 نقاط على الأقل). إذا لم توجد أي منطقة فعالة، يعمل النظام بالنطاق الافتراضي لتسهيل التطوير. عند إضافة مناطق فعالة يصبح التحقق إلزاميًا.

### ملاحظات PWA
الـ Service Worker يعمل فقط على HTTPS أو localhost. بعد كل إصدار غيّر اسم `CACHE` في `sw.js` لضمان تحديث App Shell لدى المستخدمين. للاستخدام الإنتاجي يفضّل إضافة أيقونات PNG متعددة المقاسات وتهيئة صفحات Offline أكثر تخصيصًا.

## Phase 11 — Safety, Trust & Driver Compliance
- Safety Events / SOS are created server-side and written to `safetyEvents` with audit logging.
- Secure trip-share tokens expire after 6 hours; raw trip data is not made public by Firestore rules. A production share landing page can exchange the token through a callable/HTTP endpoint.
- Mutual reputation: passengers keep the existing driver rating flow; `driverRateCustomer` adds a server-enforced one-rating-per-trip customer rating.
- Driver compliance sweep evaluates license/registration/insurance expiry fields and writes `documentStatus` (`valid`, `expiring`, `expired`). Populate `licenseExpiresAt`, `vehicleRegistrationExpiresAt`, and `insuranceExpiresAt` on driver documents.
- Risk monitoring flags unusually long active trips and opens a safety review event for administrators.
- Before production, connect SOS events to a staffed operations workflow and local emergency guidance; do not represent the in-app SOS button as a replacement for emergency services.

## إصلاح تشخيص الحجز وقبول الكابتن
تم تحديث الواجهات بحيث تعرض سبب الخطأ الحقيقي القادم من Firebase Functions بدل الرسائل العامة. من الأمثلة: خدمة Function غير منشورة، الحساب ليس customer/driver، الكابتن غير متاح، الطلب ضمن جولة توزيع لكباتن أقرب، الموقع خارج Service Area، أو مشكلة شبكة.

بعد رفع هذه النسخة، يجب نشر الـ Backend والقواعد من مجلد المشروع (وليس Hosting فقط):

```bash
firebase use karwa0
cd functions && npm install && cd ..
firebase deploy --only functions,firestore:rules,storage
firebase deploy --only hosting
```

تأكد في Firebase Console أن Functions التالية موجودة على الأقل: `createRideOrderV2`, `quoteRide`, `cancelOrderV2`, `acceptOrder`, `advanceTrip`. كما يجب أن يكون مستند `users/{uid}` للراكب بقيمة `role: customer`، ومستند الكابتن `users/{uid}` بقيمة `role: driver` مع وجود `drivers/{uid}` وأن `online: true` عند قبول الطلب.

ملاحظة التوزيع: خلال أول 30 ثانية من إنشاء الرحلة قد يرفض الخادم قبول كابتن غير موجود في `dispatchCandidateIds` برسالة `NOT_IN_DISPATCH_ROUND`. الواجهة الآن تشرح ذلك بدل عرض «تعذر تنفيذ العملية».

## تحديث أنواع التسجيل
أصبحت شاشة إنشاء الحساب تعرض ثلاثة أنواع مستقلة: عميل، كابتن، وخدمات أخرى. حساب خدمات أخرى مخصص لمزودي الخدمات مثل المطاعم ولا يتحول إلى حساب كابتن عند اعتماده.

## Phase 34 — بوابة الخدمات الأخرى والاعتماد الإداري

- زر «خدمات أخرى» في الصفحة الرئيسية يفتح بوابة مستقلة للتسجيل أو الدخول.
- إنشاء حساب خدمة يحفظ بيانات النشاط وينشئ طلبًا بحالة `pending` داخل `serviceApplications` في عملية واحدة.
- يبقى صاحب الطلب في شاشة متابعة مباشرة، ولا يفتح لوحة الخدمة قبل أن تغيّر الإدارة دوره إلى `serviceProvider`.
- لوحة الإدارة تعرض طلبات مزودي الخدمات في قسم مستقل عن طلبات الكباتن، مع قبول ذري أو رفض مرفق بملاحظة.
- عند القبول يُنشأ ملف معتمد داخل `serviceProfiles`، وتُفتح لوحة مزود الخدمة تلقائيًا من دون إعادة تسجيل الدخول.
- لوحة مزود الخدمة تدعم ملف النشاط، التصنيف، الموقع، الإظهار المؤقت، وقائمة الخدمات أو المنتجات.
- المطاعم المعتمدة تتزامن مع مجموعة `restaurants` للمحافظة على ظهور الوجبات في تطبيق العميل.
- قواعد Firestore تمنع الحساب من اعتماد نفسه أو تعديل حقول الاعتماد، وتسمح فقط للإدارة بمنح صلاحية `serviceProvider`.

### مسار التفعيل

1. افتح `services.html?mode=register` أو اختر «تسجيل خدمة جديدة» من الصفحة الرئيسية.
2. أنشئ الحساب وأكمل بيانات النشاط؛ يُرسل الطلب تلقائيًا إلى الإدارة.
3. افتح `admin.html` بحساب دوره `admin`، ثم راجع قسم «طلبات مزودي الخدمات».
4. اختر «قبول وتفعيل» لفتح لوحة الخدمة، أو «رفض مع ملاحظة» لإتاحة التصحيح وإعادة الإرسال.

> يجب نشر `firestore.rules` المرفق قبل اختبار دورة الاعتماد الجديدة.

## Phase 35 — الهوية الموحدة وسوق الخدمات

- توحّدت الألوان الأساسية في صفحات العميل والكابتن والإدارة مع هوية بوابة الخدمات الأخرى: الكحلي والأخضر المزرق والخلفيات الفاتحة.
- أصبح تحديد موقع GPS للنشاط إلزاميًا عند تسجيل خدمة جديدة أو إعادة إرسال الطلب، ويُنسخ الموقع إلى ملف النشاط عند موافقة الإدارة.
- أضيف تبويب «خدمات أخرى» للعميل يعرض الأنشطة المعتمدة والنشطة، بما فيها المطاعم والماركت، مع الاسم والتصنيف والعنوان وإحداثيات الموقع.
- يستطيع العميل اختيار نشاط وخدمة أو منتج، كتابة تفاصيل الطلب وموقعه، ثم إرسال طلب مباشر إلى المزود.
- أضيفت مجموعة `serviceRequests` لمتابعة الطلبات؛ يستطيع المزود القبول أو الرفض مع ملاحظة أو إكمال الخدمة، ويستطيع العميل إلغاء الطلب ما دام قيد الانتظار.
- تظهر حالات الطلب لحظيًا للطرفين، وتمنع قواعد Firestore كل طرف من تعديل الحقول التي لا تخصه.

> انشر `firestore.rules` الجديدة قبل اختبار سوق الخدمات والطلبات المباشرة.

## Phase 37 — التسعير والتوصيل حسب النطاق بدون رفع صور

- أزيل رفع صور الوجبات والخدمات بالكامل من واجهة المزود ومنطق التطبيق وقواعد التخزين.
- يحدد صاحب النشاط سعر الوحدة وطريقة الحساب: قطعة/طلب، كيلوغرام، أو نفر، ويضيف وصفًا تفصيليًا.
- يمكن تحديد توفر التوصيل وأجرته لكل عنصر بصورة مستقلة؛ ويختار العميل الاستلام من النشاط أو التوصيل.
- تعرض صفحة العميل كل عنصر بوصفه وسعر الوحدة، وتحسب الإجمالي مباشرة من الكمية أو الوزن أو عدد النفرات، ثم تضيف أجرة التوصيل فقط عند اختياره.
- بعد قبول مزود الخدمة، ينشأ طلب توصيل مستقل تلقائيًا داخل `orders` إذا اختار العميل التوصيل.
- طلب توصيل النشاط لا يظهر ولا يمكن قبوله إلا لحساب كابتن نوعه `delivery` وتطابق مدينته `serviceCity` الخاصة بالنشاط.
- يتابع العميل طلب النشاط وحالة كابتن التوصيل من الواجهة نفسها، ويظهر طلب التوصيل أيضًا ضمن طلباته المعتادة.

### متطلبات النشر للمرحلة 37

```bash
firebase deploy --only firestore:rules
firebase deploy --only hosting
```

لا تحتاج خدمات المطاعم والمتاجر إلى نشر `storage.rules` بعد إزالة رفع الصور. يجب نشر `firestore.rules` حتى تعمل عملية تحويل الطلب المقبول إلى كابتن التوصيل ضمن المدينة نفسها.


## Phase 42 — موافقة الإدارة على حساب الكابتن
- عند إنشاء حساب كابتن يتم إنشاء طلب `driverApplications` بحالة `pending` فورًا ليظهر للإدارة.
- يكمل الكابتن بيانات المركبة والهاتف والمدينة، ثم يصبح الطلب جاهزًا للاعتماد.
- لا تستطيع الإدارة تفعيل طلب ناقص.
- لا تُفتح لوحة تشغيل الكابتن إلا بعد أن تغيّر الإدارة دوره إلى `driver` عند الموافقة.
- الحساب المعلّق يبقى في شاشة الطلب/المراجعة ولا يصل إلى الطلبات أو لوحة التشغيل.

## Phase 43 — التسجيل المباشر للكابتن ثم موافقة الإدارة
- زر إنشاء حساب الكابتن ينقل مباشرة إلى نموذج تسجيل الكابتن الكامل في `driver.html?mode=register`.
- لا يتم إنشاء طلب إداري ناقص عند إدخال البريد وكلمة المرور فقط.
- يُنشأ حساب Firebase ودور `driverApplicant` فقط بعد إكمال بيانات الكابتن المطلوبة وإرسال النموذج.
- يُنشأ `driverApplications/{uid}` بحالة `pending` و `profileComplete: true` بعد التسجيل المكتمل.
- لا تُفتح لوحة التشغيل ولا استقبال الطلبات قبل أن تعتمد الإدارة الطلب وتحول الدور إلى `driver`.
- بعد موافقة الإدارة يعمل تسجيل الدخول بنفس البريد وكلمة المرور ويفتح حساب الكابتن المعتمد.


## Phase 45 — إصلاح تصنيف كابتن الدراجة في لوحة الإدارة
- الدراجة تُحفظ وتُعرض دائمًا كخدمة `delivery` (توصيل أغراض وطعام)، ولا يمكن أن تظهر كتـكسي.
- لوحة الإدارة تطبع اسم الخدمة من دالة توحيد تدعم السجلات القديمة (`توصيل`، `parcel`، `food`، `serviceDelivery`) بدل اعتبار كل قيمة غير `delivery` تكسي.
- عند اعتماد كابتن، يتم تصحيح `serviceType` إلى القيمة القياسية (`delivery` أو `taxi`) قبل إنشاء سجل `drivers`.
- عند اختيار الدراجة في نموذج التسجيل، يتم تحويل نوع الخدمة تلقائيًا إلى «توصيل» ويُحفظ كذلك حتى لو كان الاختيار السابق تكسي.

## Phase 46 — توزيع الطلبات حسب التصنيف ونطاق 10 كم
- لا يظهر طلب للكابتن إلا إذا كان نوعه مطابقًا لتصنيف الحساب: `taxi` لطلبات `ride` فقط، و`delivery` لطلبات `parcel` / `food` / `serviceDelivery` فقط.
- الطلبات المتاحة والإشعارات الجديدة تُفلتر حسب موقع GPS الحي للكابتن وبمسافة Haversine لا تتجاوز **10 كم** من نقطة بداية الطلب.
- نقطة بداية التكسي هي موقع صعود العميل، ونقطة بداية توصيل الطعام/الخدمات هي موقع المطعم أو النشاط، ونقطة بداية توصيل الغرض هي موقع الاستلام.
- إذا لم يكن GPS متاحًا للكابتن، لا تظهر له طلبات متاحة حتى يتم تحديد موقعه.
- قبل قبول الطلب يعاد حساب المسافة، لذلك لا يمكن قبول بطاقة أصبحت خارج نطاق 10 كم بعد تحرك الكابتن.
- أضيف تحقق إضافي داخل `firestore.rules` على قبول الطلب لمنع تجاوز شرط النطاق من واجهة معدلة.
- طلب توصيل الغرض يتطلب تحديد موقع الاستلام عبر GPS حتى يمكن إدخاله في نظام نطاق 10 كم.

> بعد رفع Phase 46 يجب نشر `firestore.rules` الجديدة، ثم رفع ملفات الاستضافة.
